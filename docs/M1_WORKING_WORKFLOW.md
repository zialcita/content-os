# Tested private-source workflow

Date: 2026-09-14 UTC. Baseline b63ffbf52f85e4d52905c5ec1d32974ac5578cba. This checkpoint delivers a real local development workflow, not a complete R1 pilot or production deployment.

## Working path, demonstrated in Chromium

1. Open the same-origin development workbench at /api/v6/workflow.
2. Sign in through authorization code/PKCE. Automated acceptance uses a cryptographically signed fixture IdP, explicitly labeled; no live account proof is claimed.
3. Choose an authorized workspace and brand.
4. Select an actual UTF-8 text file and supply a title/rights assertion.
5. Create an idempotent private upload intent; transfer bounded immutable parts with optimistic concurrency. The database stores part sizes/hashes and supports resume/replay.
6. Finalize into a persisted ingestion job, returning202 and a real status URL. Transfer completion leaves the file quarantined, with no ready source version.
7. A separate restricted worker claims the job, reads actual private file bytes, validates size/hash/UTF-8 and text policy, then commits a fenced terminal result and sealed source version.
8. The workbench polls actual status and displays the exact validated source text, hash, byte count and immutable version ID. Metadata revision creates a new version without changing old content/history.

Browser evidence is generated by tests_content_core/test_ui.py using Chromium. Browser requests are bridged locally into actual ASGI/PostgreSQL; the IdP response is a signed fixture. Redirect navigation is represented by equivalent local test navigation because Playwright route interception does not transparently follow all synthetic redirect hops. The application itself returns303 with real session cookies, which the bridge asserts. There are no fabricated processing percentages or completion responses. A screenshot accompanies the thread delivery; text-only repository commits do not contain its binary bytes.

## Implemented boundaries

- New additive revision0003_content_core; committed001/002 SQL is unchanged. It adds12 forced-RLS content/ingestion/version tables and fixed-search-path definer routines.
- Runtime role gets only an explicit content-function allowlist, no direct content table access. Worker has separate restricted login authority, opaque claim capabilities, session-user binding, fencing and current originating-actor revalidation.
- Identity/combined migration audits now recognize the explicitly reviewed content extension; unexpected function/table grants remain rejected. Original foundation and identity suites keep revision-specific assertions, with a separate full-head003 audit test.
- Private local storage is explicitly development-only: owner-only directories, UUID-only namespaces, dirfd/O_NOFOLLOW traversal, immutable part writes, no public URLs, symlink/hardlink/FIFO protection and bounded reads.
- Files are never previewed merely because transfer finishes. Reader access requires a cleared source version and current tenant/brand permissions.
- Worker validates actual bytes. The current implemented policy is TEXT_POLICY_V1 plus UTF8_BOUNDS_V1: bounded UTF-8 decoding, control/binary checks, source size and SHA-256 checks. This is NOT a general malware engine or antivirus certification.
- PDF/WAV/MP4 may be privately transferred but are BLOCKED with SCANNER_UNCONFIGURED; they cannot produce a ready source. Unsupported formats are rejected. Real cloud storage and broader media scanners are external/integration gates, not silently simulated.
- Request and worker budgets are non-paid. This ingestion queue is separate from the prior LOCAL_SIMULATION production-job prototype and exposes its own typed status endpoint. Future queue unification remains required; no paid job or publication authority is granted here.
- Source registry enforces a matching concrete source subtype, immutable sealed content, normalized references, same-tenant FKs/current pointers, metadata revision lineage and cycle checks. Only source versions are enabled; this is not the entire asset/approval registry.

## API surface

Under /api/v6/workspaces/{workspace_id}/brands/{brand_id}:
- POST/GET upload-intents and a specific upload-intent.
- PUT upload-intents/{upload_id}/parts/{part_number}; bounded8MiB chunks, If-Match required.
- POST sources/{source_id}/finalize; Idempotency-Key/If-Match required, actual202 job acknowledgement.
- POST upload-intents/{upload_id}/cancel; cancels/fences ingest and queues restricted purge.
- GET ingestion-jobs/{job_id}; persisted state/events, never provider simulation.
- GET/PATCH sources/{source_id}; metadata revision is immutable/versioned.
- GET source-versions/{version_id}; private object keys omitted.
- GET sources/{source_id}/versions/{version_id}/content; bounded JSON text preview, not HTML execution or a complete export archive.

The extra development part-transfer, ingestion-job and preview endpoints are explicit implementation deltas from the target S3-presigned/full-export contract. Runtime OpenAPI has typed requests/responses; target-v6 remains the wider planned contract. Do not serve the target as implemented endpoints.

## Reproduce local evidence

Use a clean Python3.12 virtual environment with backend/requirements.lock, schema test dependencies from docs/evidence/m0/m0-tools.lock, pgserver0.1.4 and browser-test dependencies in backend/requirements-browser-tests.lock. Install Chromium using python -m playwright install chromium. Then run:

    python scripts/test_content_core_postgres.py "$PWD/.venv/bin/python"

The outer interpreter must have pgserver. The script creates a fresh local PostgreSQL cluster and allowlisted child environment; no inherited DATABASE_URL, .env or live provider credentials. It creates only fictional test accounts and private temporary data. Actual source code, fixtures, runtime schema, hashes and logs are captured under docs/evidence/m1/content-core.

## Running the development application and worker

content_core.workbench.build_workflow_app(settings, runtime_engine, authentication_engine, store) composes the existing secure factory, content router and workbench. Supply only the reviewed restricted service roles and exact HTTPS/OIDC settings; no admin connection or public signup is accepted. This is not automatically provisioned or deployed.

The separate worker entrypoint is python -m content_core.run_worker with explicit workspace, brand, private-root and --development. Its dedicated connection is supplied through CONTENT_WORKER_DATABASE_URL, never an inherited generic DATABASE_URL; role validation refuses administrator credentials. --once processes one claim; otherwise it polls the persisted queue. No HTTP process or browser timer performs worker execution.
