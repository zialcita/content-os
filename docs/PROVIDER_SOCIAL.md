# Content OS R1 — M0 direct-publishing provider capability research

**Research date:** 2026-09-11 UTC (sandbox clock). **Evidence class:** official provider documentation, retrieved through Exa search/content; some Meta live reads timed out and cached official excerpts were used. This is a dated documentation snapshot, not a claim that every page was freshly crawled. Provider sample versions and conflicting limits are explicitly flagged below.

**Scope:** five mandatory direct destinations: YouTube (long form AND Shorts), LinkedIn text (personal and company capabilities researched separately; the owner selects the required account type), Instagram Reels, Facebook Page Reels, TikTok video. Seven matrix rows express format/account variants, not seven destinations. Downloads, generated files, inbox drafts, manual posting, and crossposting to only one platform never substitute for any mandatory direct destination.

**Result:** documented direct-publishing mechanisms exist for all five providers, but R1 release is **NOT VERIFIED / BLOCKED pending owner gates**. No account, OAuth, app review, quota, production endpoint, publication, deletion, spending, or configuration action was performed. All account verification values are `not_done`; all observed account metrics are `null`. This sandbox cannot satisfy a real release gate.

Zero is allowed only when returned or explicitly defined by that endpoint's documented empty-result semantics. Do not use absence of analytics as evidence of publication failure.

## 4. Uncertain outcomes, verification and release tests

Canonical publication states remain exactly v6 section 15.2. Terms such as uploaded, published_unverified, live_verified, needs_reauth and outcome_unknown in this research describe provider evidence, not replacement application enum values. Map uncertain acceptance to RECONCILING, incomplete verification to PROCESSING, verified requested-visibility publication to PUBLISHED, and verified removal to TAKEN_DOWN. Preserve native provider status and verification detail separately. A processing_complete response, HTTP 2xx, remote ID, inbox receipt, scheduled acceptance or constructed URL alone is insufficient for PUBLISHED.

- Persist a durable publication attempt before network write: immutable content hash, intended account/format/privacy, consent/approval version, schedule, API/profile version, provider session/container/publish/post IDs, correlation IDs, response timestamps and redacted errors. Never log tokens or upload URLs containing secrets.
- Timeout after create/finish can mean successful publication with lost response. Reconcile stored session/ID and authorized recent posts before retry. If no reliable proof/ID exists, hold `outcome_unknown` for operator review; do not blindly replay a create and duplicate content. No universal provider idempotency key was established here.
- Use backoff/jitter respecting Retry-After and quotas; distinguish retryable transfer chunks from dangerous repeat-create. Refresh tokens securely; revoked scopes require reauthorization. Do not route one account to another as a fallback.
- Verify account ID and author at each transition. For public release capture canonical provider ID, native terminal publish status, public permalink, timestamp and independent intended-audience playback/UI evidence; for Shorts also classification. A login wall may make automated unauthenticated checking inconclusive, not failed or verified.
- Moderation/copyright/region restrictions may arrive after publication. Keep a post-live reconciler; track visibility revocation/deletion. TikTok publicly_available/no_longer_publicaly_available events differ from publish.complete. Instagram FINISHED differs from PUBLISHED. A schedule time is not a guarantee of public availability at that instant.
- Test read-after-write, token expiry, 429, duplicate prevention, lost-response reconciliation, processing failure, inaccessible/expired media URL, schedule drift, user cancellation and post-removal proof in production-equivalent infrastructure.

## 5. Concrete owner gates — required, not completed

1. **Resolve TikTok product eligibility first.** Owner must state whether Content OS is only an internal upload utility. If so, current Direct Post intended-use rules are a material eligibility blocker. Obtain provider-accepted broad-audience use case/audit approval; do not hide internal use, substitute inbox/manual/download flow, or mark the fifth destination optional. Failure keeps full R1 blocked.
2. **Provide authorized account inventory:** exact YouTube channel ID and Shorts/long-form feature eligibility; LinkedIn member and organization URNs plus organic Page role; professional IG ID, chosen login path and Page link if needed; FB Page ID/tasks; TikTok creator identity. Verify against OAuth subjects, not display names alone.
3. **Provide app/project entitlements:** Google OAuth client production posture + YouTube upload audit; LinkedIn Share on LinkedIn and required Community Management tier/scopes; Meta chosen login architecture, app mode, business verification/access review/PPA/2FA as applicable; TikTok Direct Post config, approved scope, audit and caps. Screenshots alone do not replace token capability checks.
4. **Deploy real secure backend:** owner-controlled HTTPS OAuth callbacks and TikTok URL ownership if pull is used; encrypted token storage/refresh, durable worker/queue, database/outbox, media storage with sufficient lifetime, validated webhook receiver, logs/alerts, production observability. A static webpage or temporary sandbox cannot reliably hold schedules or complete publication reconciliation.
5. **Approve content/consent UX:** per-destination exact media/text, account, privacy, timing, rights/licenses, AI/synthetic/branded labels, interaction settings and cancellation boundary. TikTok privacy has no preselected default; current creator metadata must drive UI. Facebook Page Reels are public. No delegated research approval authorizes any publication.
6. **Approve separate live acceptance tests:** explicit owner permission for real posts and, separately, destructive cleanup; one real successful direct publish for each mandatory destination and both YouTube formats, plus both LinkedIn actor types if required by R1; canonical IDs/public evidence; metrics authorization/nullable behavior; deletion or clearly disclosed owner-only removal contingency; lost-response and schedule tests. Sandbox tests are prerequisites, not real-publication evidence. Real private tests prove only the explicitly approved private visibility; separate public tests are needed to claim public eligibility.
7. **Pin profiles and resolve doc drift:** actual project quotas; LinkedIn version/entitlements; Meta Graph version, IG50/100 cap, selected login-path delete rights, FB media/scheduling/deletion behavior; TikTok creator caps/maximum duration. Attach evidence and reviewer signoff to each gate. Do not replace missing facts with optimistic defaults.

**Release decision:** documentation research can pass M0 discovery, but account verification, provider approval and real E2E release remain explicitly incomplete. No “five direct destinations ready” claim is supportable from this task.
